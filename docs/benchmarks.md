# CachePulse 压测记录（2026-11-24～28）

所有压测都在 Instabox 上跑：一台 4 vCPU / 8 GB 的机器，MySQL 8、Kafka、Canal 1.1.8、Redis 6.2 和全部服务都在这台机器上。结果反映的是这台机器的上限，不是分布式部署的上限。

每组的汇总数据在 `docs/benchmarks/data/`，`rounds.json` 是每一轮的吞吐、缓存失效分位数和积压峰值。完整原始样本在本机 `records/`（不进 git），服务器上的结果打包在 `records/cachepulse-cleanup-20261126/server-results-20261126.tar.gz`（sha256 `037a7e1f…`，993 个文件）。

## 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 低负载下删缓存多快 | 逐条写入、随机间隔时，P50 从 55.7 ms 降到 13.4 ms，P99 从 109.4 ms 降到 29.4 ms | 第 4 节 |
| 拆分后和单体比 | 3 路闭环 P99 更稳（111～113 ms 对 116～309 ms）；32 路时写入少约 20%；消息到删缓存这一段 P99 快约 3 倍，归档不再积压 | 第 2 节 |
| 投递接收端出故障 | Webhook 一直返回 500，删缓存 P99 从 148 ms 到 157 ms，基本不受影响 | 第 3 节 |
| 高负载长尾 | 慢请求在演示用户服务里等数据库连接；占着连接的事务卡在 MySQL 提交。加大连接池、调 CPU 权重都没用；后台写入节奏 650 行/秒在 75 秒压测里把 P99 从 431 ms 降到 181 ms，默认关闭 | 第 6～8 节 |
| Canal 补丁的代价 | 同一组交替比较，写入不比原版少；Canal 空闲 CPU 从一个核的 0.8% 升到 2.5% | 第 4、9 节 |
| 按主键查历史多快 | 旧 SQL 倒着扫主键，4.7～13.8 秒，经网关超时返回 503；改成按索引分路查再 UNION，SQL 0.05～17 ms，经网关 39～88 ms | 第 10 节 |

## 0. 测法和读数注意

| 名称 | 做法 |
| --- | --- |
| 缓存失效耗时 | 从发出更新请求，到探针看到 Redis 里的缓存键消失（探针每 5 ms 查一次） |
| 3 路闭环 | 3 个线程，每个 100 次；缓存删掉后才写下一次 |
| 32 路 | 32 个线程连续写 20 秒（第 7 节有 75 秒的），另有 3 路探针按闭环方式测缓存失效 |
| 逐条随机间隔 | 一次只写一个部门，间隔随机 150～450 ms，共 80 次；按段计时：写库、Canal、Kafka、删缓存 |

- 同样的设置，不同轮次差得很多。例：第 7 节同是 CPU 权重 100，第一轮每秒 633 次，最后一轮 1007 次。每组第一轮常偏慢。
- 所以只比较同一组里交替跑的轮次；跨组、跨时间的数字不直接比。
- 32 路时整台机器 CPU 82～95%，写入吞吐主要受 CPU 限制。
- 单体那几轮是临时容器，跑的时候 CachePulse 的 4 个服务停着，公网页面会暂停约 1 分钟。

## 2. 单体和 CachePulse 交替各 3 轮（11-25，`records/cachepulse-ab-20261125`）

两版都直接打业务容器，交替跑 3 轮。数据：`data/ab-monolith-vs-cachepulse.json`、`data/ab-high-load-segments.json`。

| | 单体 | CachePulse |
| --- | --- | --- |
| 3 路 P50 | 93～97 ms | 96～98 ms |
| 3 路 P99 | 116～309 ms | 111～113 ms |
| 32 路每秒写入（中位） | 945 | 755 |
| 32 路缓存失效 P99（中位） | 314 ms | 433 ms |
| 32 路：Kafka 收到到删掉缓存 P99 | 203～248 ms | 61～87 ms |
| 32 路：归档积压峰值 | 4207～4435 条 | 51～56 条 |
| 停写后归档追平 | 2.8～6.3 秒 | 0.2～0.7 秒 |

拆分后同步服务独占消费，消息到删缓存这一段更快。写入吞吐低的一个原因是投递服务的去重写入：第 6 节暂停投递后，每秒写入从 441～775 升到 786～886。

| --- | --- | --- | --- | --- |

## 4. Canal 空批等待（11-25，`records/cachepulse-latency-breakdown-20261125`、`records/cachepulse-canal-tune-20261125`）

逐条随机间隔，80 次，线上补丁前后各一次。数据：`data/idle-latency-before-canal-patch.json`、`data/idle-latency-after-canal-patch.json`。

| 一段 | 补丁前 P50 | 补丁后 P50 | 补丁前 P99 | 补丁后 P99 |
| --- | --- | --- | --- | --- |
| 写库 | 4.1 ms | 5.8 ms | 7.3 ms | 13 ms |
| Canal | 48.4 ms | 2.4 ms | 103.6 ms | 6.8 ms |
| Kafka | 2 ms | 3 ms | 11 ms | 13 ms |
| 删缓存 | 1 ms | 1 ms | 3 ms | 5 ms |
| 合计 | 55.7 ms | 13.4 ms | 109.4 ms | 29.4 ms |

补丁前 Canal 这一段在 0～100 ms 之间均匀分布：Canal 1.1.8 的 `CanalMQStarter` 拿到空批后固定睡 100 ms（补丁见 `docker/canal/patch/`）。

补丁前先在临时的第二个 Canal 上比了 5 组设置（只读 `demo_db.departments`，写到自己的 topic，每秒 700 次固定写入）。数据：`data/canal-settings-temporary-instance.json`。

| 睡 / 等 / 批 | 空闲 CPU（一个核） | 空闲 P50 | 每秒 700 次 P50 | 每秒 700 次 P99 |
| --- | --- | --- | --- | --- |
| 100 / 5 / 16（原版） | 0.8% | 51 ms | 40 ms | 119 ms |
| 1 / 5 / 16 | 1.9% | 4.8 ms | 12 ms | 73 ms |
| 1 / 1 / 16（线上采用） | 2.5% | 1.8 ms | 7.3 ms | 46 ms |
| 1 / 5 / 64 | 1.8% | 4.3 ms | 15 ms | 63 ms |
| 1 / 1 / 64 | 2.6% | 1.9 ms | 7.9 ms | 71 ms |

表里只是 Canal 这一段（Kafka 记录生成时间减去写请求返回时间）。

## 5. 补丁后单体和 CachePulse 交替各 3 轮（11-25，`records/cachepulse-ab-after-canal-20261125`）

和第 2 节同一套脚本。数据：`data/ab-before-after-canal-patch.json`、`data/ab-tail-segments-before-after-canal-patch.json`。

| | 单体 | CachePulse |
| --- | --- | --- |
| 3 路 P50 | 15～18 ms（补丁前 93～97） | 19～24 ms（补丁前 96～98） |
| 3 路 P99 | 32～268 ms | 42～53 ms |
| 32 路每秒写入 | 704～775（补丁前 799～980） | 532～574（补丁前 488～844） |
| 32 路缓存失效 P99 | 348～660 ms | 224～605 ms |
| 32 路 Canal 容器 CPU | 37～46%（补丁前 23～33%） | 同左 |

32 路时最慢的 5% 探针（CachePulse）：写库 167～319 ms，Canal 6～8 ms，Kafka 之后 15～19 ms。长尾在写库，不在 Canal。

这组和第 2 节隔了约 2 小时。写入变少当时怀疑是 Canal 发得更勤；第 9 节在同一组里交替比较后，打补丁的设置写入并不比原版少，所以这里的差别来自机器状态。

## 6. 写入慢在哪（11-25，`records/cachepulse-write-diagnosis-20261125`）

临时演示用户实例，32 路 20 秒，交替暂停投递服务。

| 投递服务 | 每秒写入 | 缓存失效 P99 |
| --- | --- | --- |
| 运行 | 441（第一轮）、775、658 | 240、171、167 ms |
| 暂停 | 886、865、786 | 151、136、142 ms |

投递服务对每条变更都写一条去重记录，和业务写入共用 MySQL。

投递同一批消息只查一次订阅（`0a997e4` 里的改动），原版和优化版交替各 2 轮（`records/cachepulse-delivery-sql-ab-20261125`）：每秒写入 515、768 对 788、781，P99 533、569 对 503、464 ms；固定每秒 450 次时（`records/cachepulse-delivery-rate-ab-20261125`）P99 144、60 对 42、106 ms。差距在波动范围内，没有结论。

## 8. 高负载长尾和后台写入节奏（11-25～26）

`records/cachepulse-mysql-wait-20261125`：目标每秒 800 次，实际 690 次，缓存失效 P50 23.5 ms，P99 570 ms。MySQL Performance Schema 显示一批更新卡在 `waiting for handler commit`，最长 589 ms；后面的写请求在演示用户服务里等连接。同样的设置在 `records/cachepulse-disk-canary-20261125` 里 P99 是 124 ms，长尾是间歇出现的。

后台写入节奏：归档、投递每批提交并确认 Kafka 位点后，在事务外按目标行数补足间隔（`-Dcachepulse.background-write-rows-per-second`，默认 0）。

| 试验 | 节奏 | 每秒写入 | P50 | P99 | 积压峰值（归档 / 投递） | 停写后追平 |
| --- | --- | --- | --- | --- | --- | --- |
| 12 秒短测（`cachepulse-background-pace-20261125`） | 0 / 650 / 650 / 0 | 474 / 721 / 794 / 742 | 62 / 40 / 17 / 42 ms | 236 / 125 / 80 / 144 ms | 130、1103、1120、1617 / 43、638、1147、149 | — |
| 75 秒（`cachepulse-background-pace-long-20261126`） | 0 / 650 | 629 / 705 | 49 / 48 ms | 431 / 181 ms | 1223、1513 / 394、901 | 1.4 / 3.7 秒 |

75 秒那组两轮都逐行核对了归档和投递去重表，数据一致，临时数据清理干净。

开着节奏再按段计时（`records/cachepulse-canal-path-20261126`，数据 `data/tail-segments-with-pacing.json`）：每秒 502 次，P99 464 ms；最慢的 2% 平均 393 ms 在等连接，Canal 这一段约 24 ms。剩下的长尾在连接池排队。

## 9. Canal 设置同场对比（11-26，`records/cachepulse-canal-ab-20261126`）

只跑 CachePulse，在同一组里交替切换 Canal：每轮换 jar 和 `canalGetTimeout`，重启 canal-server，等到 FRESH 且积压为 0 再测。先跑一轮预热（不计），然后按「原版、1/1、1/5、1/5、1/1、原版」排，每种设置前后半段各一轮。每轮做 3 路闭环、32 路 20 秒、逐条随机间隔 80 次。数据：`data/canal-settings-live-ab.json`。

| 设置（睡 / 等） | 轮次 | 3 路 P50 | 32 路每秒写入 | 32 路 P50 | 32 路 P99 | 逐条：Canal 段 P50 | 逐条：合计 P50 / P99 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 100 / 5（原版） | 1、6 | 103 / 101 ms | 956 / 783 | 102 / 109 ms | 277 / 573 ms | 53 / 56 ms | 59～61 / 108～109 ms |
| 1 / 1（线上） | 2、5 | 11 / 10 ms | 960 / 819 | 54 / 42 ms | 455 / 565 ms | 0.7 / 0.7 ms | 5.8～5.9 / 13～18 ms |
| 1 / 5 | 3、4 | 12 / 12 ms | 1015 / 957 | 54 / 54 ms | 158 / 375 ms | 2.7 / 2.5 ms | 7.8～8.5 / 17 ms |

- 同一组里，打补丁的两种设置写入都不比原版少（前半段 960、1015 对 956，后半段 819、957 对 783）。第 5 节看到的写入下降，是两组相隔两小时、机器状态不同造成的，不是 Canal 设置造成的。
- 后半段三种设置的写入都比前半段低，那几轮整机 CPU 只有 71～79%（前半段 86～90%），机器本身在变慢。
- 1/5 在 32 路下两次都略好，1/1 空闲时快约 2 ms；每种只有 2 轮，差距在波动范围内。线上保持 1/1。
- 32 路 P99 三种设置都在 158～573 ms 之间跳，长尾不由 Canal 决定（第 8 节）。

## 10. 按主键查历史（11-28，`records/cachepulse-history-search-20261128`）

管理页面"变更历史"按主键值筛选，调的是归档服务 `GET /platform/events?key=`。线上 `change_event` 约 112 万行、2.9 GB，其中 `departments` 126.7 万行（大多是压测写入），InnoDB 缓冲池 128 MB。数据：`data/history-key-search.json`。

| | 旧查询 | 新查询（`f7e0dd7`） |
| --- | --- | --- |
| SQL | 一条：`(primary_key_value=? OR before_primary_key_value=?) ORDER BY sequence_id DESC LIMIT 21` | 每张表、每个主键列各一路，各取前 21 条，`UNION` 去重后再取前 21 条 |
| 执行计划 | `Index scan on change_event using PRIMARY (reverse)`：倒着扫主键、逐行过滤，优化器估计扫 41 行就够 | 每一路 `Index lookup ... using idx_event_table_key`（或 `idx_event_table_old_key`），倒序读到 21 条就停 |

| 主键值 | 命中（主键 / 旧主键） | 旧查询 | 新查询（EXPLAIN ANALYZE） | 结果一致 |
| --- | --- | --- | --- | --- |
| 996 | 212 / 211 | 13.2、13.8 秒 | 7.6～17.4 ms | 是 |
| 1340（压测更新最多的部门） | 2621 / 2620 | 4.7 秒 | 4.8～7.3 ms | 是 |
| 987654321（不存在） | 0 / 0 | 5.8 秒 | 0.05～0.07 ms | 是 |

- 旧查询每个值只跑 1～2 次，避免一直压着线上 MySQL；时间受缓存影响，只看量级。
- 经网关（服务器本机 curl，不含公网）：上线后 6 种按主键的查询各 3 次全部 200，39～88 ms，和不带主键的翻页（49～109 ms）一样。上线前从公网按主键查 12 次全部 503（网关超时 5 秒）。
- 从公网访问，每个请求都要约 2 秒（静态文件也是），这是公网链路本身的耗时。上线后公网按主键查 15 次全部 200，2.0～2.3 秒。
- 测试：`ArchiveKeySearchTest`（H2）和 `ArchiveKeySearchMysqlTest`（真实 MySQL，CI 不许跳过）覆盖两列都能命中、去重、倒序、分页和表、操作筛选。
